# Waybill

> 可审计的跨系统流程 Agent

把 OA 里审批完的报销单搬进财务系统：agent 负责在浏览器里执行，人负责签收。

## 背景

国内大量企业的 OA 和财务系统是两套独立采购、独立演进的老系统，中间没有接口。一张报销单在 OA 里审批通过后，财务还要在另一个系统里把十几个字段、几行明细、几张发票再录一遍：

- 一天 30 单，就是 360 次手工输入，和 30 次可能的错位
- 制度判断（科目怎么归、成本中心是谁、这张票是不是报过）全靠人记
- 出了问题查不到过程，只能翻纸质单据

三种现成方案都解决不了这件事：

| 方案 | 为什么不行 |
|---|---|
| RPA | 选择器写死，页面改版就全崩，维护成本高于人工 |
| API 集成 | 老系统不开放接口，厂商改造周期以季度计 |
| OCR | 只解决发票识别，不解决"往另一个系统里填" |

Waybill 的思路：让 agent 在浏览器里像人一样执行，但比人多了三件事——**页面变了能自己修、做完能自己核验、每一步都留痕可查**。

> 说明：真实企业的 OA / 财务系统无法获取，本项目自建两套仿真系统来承载这个场景。仿真系统刻意做成异构，并支持"漂移模式"（`?ui=v1|v2|v3`），用于可复现地测试自愈能力。

## 为什么叫这个名字

一次执行 = 一票货。整个领域模型用物流隐喻统一，代码和文档不会各叫各的：

| 概念 | 隐喻 |
|---|---|
| Task | 一票货 |
| Run | 一次运输 |
| Recipe | 固定航线（参数化后可复用） |
| Step / Trace | 行驶轨迹 |
| Evidence | 随车单据（截图、DOM 快照、网络响应） |
| Human gate | 签收 |
| Verification | 验货 |
| Audit view | 这张运单本身 |

## 三条设计底线

1. **重放不调 LLM** —— LLM 只在两处出现：定位失败时的自愈、业务字段的判断
2. **LLM 写意图，运行时写事实** —— 审计日志不能由模型自述，否则它错了日志也错
3. **提交必须人点** —— agent 只制单，`maker` / `checker` 分权，接口层强制

## 路线

顺序是刻意的：**先把靶子立好并上线冻结，再动真正的产品**。

| 阶段 | 内容 | 状态 |
|---|---|---|
| 1 | OA 仿真系统 | ✅ 完成 |
| 2 | 财务仿真系统（FastAPI + React SPA） | 进行中 |
| 3 | 两套系统部署上线，之后不再改动 | 待做 |
| 4 | **Waybill Agent 服务 + 控制台**（重点） | 待做 |

靶子是耗材，做完就冻结；真正的工程量在 Agent 服务和控制台。
