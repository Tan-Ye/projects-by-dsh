# 决策日志

每选一次技术，记一条：**选了什么 / 为什么 / 放弃了什么 / 代价是什么**。

留下理由，是为了让后来的人（包括三个月后的自己）不必重新论证一遍，也能看清每个选择的边界。

---

## D1 · OA 仿真用标准库 `http.server` + Jinja2

**背景**：OA 是"老系统"的仿真，只需要服务端渲染几张页面。

**选择**：Python 标准库的 `ThreadingHTTPServer`，模板用 Jinja2。

**放弃**：FastAPI。

**代价**：路由、会话、表单解析都要手写（约 400 行）。

**为什么值得**：老系统本来就不该有新框架的痕迹；而且这个环境里 pip 装不了包，标准库是零风险。后来 `tools/bootstrap.py` 解决了依赖问题，但 OA 没有再改——它能跑，就够了。

---

## D2 · 财务系统用 SPA，不用 SSR / Next.js

**背景**：目标是"给 agent 一个真实的目标系统"。

**选择**：React SPA（CSR）。

**放弃**：Next.js / SSR。

**理由（按重要性）**：

1. **异构**。OA 已经是 SSR + 整页刷新 + cookie。财务再做 SSR，两个靶子考同一类问题，项目最值钱的能力就没了。
2. **收益为零**。登录后的表单应用：没有 SEO，没有首屏内容价值。真实团队用 Next.js 做后台，最后基本整页 `'use client'`，绕一圈回到 SPA 还多背一个 Node 运行时。
3. **市场一致**。国内费控 SaaS、企业内部财务中台的主流就是 React SPA + 独立 API。

**代价**：放弃 SSR 的首屏与 SEO 能力。这套选型对内容型站点不适用，换成门户或营销页时要重新评估。

---

## D3 · 财务后端用 FastAPI

**背景**：需要在 OA（标准库）之外提供另一种后端形态，同时为后面的 Agent 服务打底。

**选择**：FastAPI + Pydantic。

**放弃**：继续用标准库；Go；Node。

**理由**：Pydantic 的模型校验天然适合"错误要结构化"这条约束；与后续 Agent 服务保持同一技术栈，减少跨栈成本。已用 `tools/bootstrap.py` 验证可安装（fastapi 0.156 / pydantic 2.14）。

---

## D4 · 借贷单边录入，贷方由系统自动生成

**背景**：费用报销凭证严格来说是双分录。

**选择**：agent 只填借方，贷方科目固定为「其他应付款-员工报销」，金额等于借方合计。

**放弃**：让 agent 手工做双分录、验借贷平衡。

**理由**：对方科目是系统规则，agent 无从得知。让它猜等于制造不公平的失败——测得出来的只是运气，不是能力。

---

## D5 · 外部单号重复，在创建草稿时就返回 409

**选择**：`POST /api/vouchers` 阶段就拦，不等提交。

**放弃**：允许创建重复草稿、提交时才拦。

**理由**：如果服务端不挡，"防重复"就变成了考验 agent 记不记得查重，而不是考验系统设计。T3 真正要测的是**收到冲突后会不会停下来如实上报**。

---

## D6 · 漂移只改呈现，不改语义

**选择**：v1/v2/v3 三个档位下，账户编码、金额、成本中心必须完全一致，`/api/state` 返回逐字节相同。

**放弃**：让 v3 真的改科目编码（`6601.03` → `6601.0301`）。

**理由**：编码变了就是数据变了。自愈率会混入"业务值不同"的噪声，测出来的数字没有意义。

**代价**：v3 的难度略低于"真改版"，但指标可信。

---

## D7 · 金额一律按「分」存整数

**选择**：所有金额字段用 `INTEGER`，单位分。

**放弃**：`REAL` / `DECIMAL` 字符串。

**理由**：浮点累加会出现 `0.1 + 0.2 != 0.3`；对账场景里，一分钱的误差就是一次误判。

---

## D8 · 评测用独立 checker，不读 agent 的自述

**选择**：checker 直接调两个系统的 `/api/state`，断言终态。

**放弃**：让 agent 汇报结果，或者解析 trace 判断成败。

**理由**：agent 说成功不算数。审计日志的价值恰恰在于它是**独立于 agent 的记录**——如果连评测都靠它的自述，整套东西就没意义了。

---

## D9 · 每个任务运行前重置数据并套用自己的夹具

**选择**：`POST /api/_reset`（带管理 token），按任务夹具重建数据。

**放弃**：让任务之间互相依赖（先跑 T1 再跑 T3 制造重复）。

**理由**：任务必须能任意顺序、独立重跑、并行执行。依赖顺序的评测集在调试时是灾难——失败到底来自代码还是脏数据，无法区分。

---

## D10 · 前端零构建方案被否

**背景**：一开始为了规避构建风险，打算用原生 ES Module 手写 SPA。

**转折**：实测 `pnpm` 可用（7 秒装完 React 19），当初的风险假设不成立；而零构建会让目标系统少两类真实难度——**React 受控输入**和 **AntD Portal**。

**结论**：改用 Vite + React + TS + AntD。

**留档原因**：记录方案被推翻的过程和依据。决策日志的价值不只在最终结论，也在留下变更的理由——否则后来的人只会看到"为什么用 React"，看不到"为什么曾经不用"。

---

## D11 · 校验放在保存，提交保持人点

**背景**：原设计是"提交必须人点，agent 只建单"。但提交时那 800ms 异步校验，agent 就永远碰不到——而这正是目标系统里最值得测的难点之一。

**第一次尝试（已否决）**：拆成三态 `draft / submitted / posted`，让 agent 提交待复核、人只负责记账。难点是保住了，但**改动了已经定下的原则**。发现冲突应该摆出来，不该自己改。

**最终选择**：原则不动，改校验的位置。

- 校验前移到**保存草稿**（`PUT /api/vouchers/{id}`，800ms），agent 必须在交付前过这一关
- 提交仍由人做，并且用 `maker` / `checker` 角色强制：agent 账号不渲染提交按钮，调接口返回 403

**放弃**：三态；以及"靠约定保证人不被绕过"。

**理由**：原则靠约定守不住，靠权限才守得住。校验放保存还有一个好处——错误在 agent 手里就暴露，不会等人签收时才发现一张烂单。

**代价**：每次保存多 800ms 等待；实现上要做角色和权限校验。

---

## D12 · 补上复核环节：draft → pending → submitted

**背景**：D11 落地后只有两态，maker 保存完就停在 `draft`，"谁来审批"没有答案——复核人只能自己去列表里找草稿，界面上也看不出"提交"是入账还是送审。

**选择**：拆成三步，`draft → pending → submitted`，新增两个接口：

| 接口 | 谁调 | 作用 |
|---|---|---|
| `POST /submit` | maker / checker | 草稿送审，进入复核队列 |
| `POST /approve` | 仅 checker | 复核通过，分配凭证号并入账 |
| `POST /reject` | 仅 checker | 退回草稿，写入 `review_note` |

**与 D11 的关系**：D11 定的是"终审必须人点"，这里没有动摇——**`approve` 是唯一能把单据变成 `submitted` 的入口，且必须 checker**。agent 用 maker 账号，能制单、能送审，但过不了复核。

**放弃**：两态 + 靠界面提示"请用 checker 登录提交"。能做，但流程藏在别人脑子里，新人看不出单据走到哪一步。

**代价**：`vouchers.status` 的 CHECK 多一个值，库里多三列（`approved_at` / `approved_by` / `review_note`），前端多两个按钮和一个驳回弹窗。schema 变更没法用 `ALTER` 改 CHECK，只能重建库——本项目数据是种子生成的，重建没有成本。

**顺带修的**：成本中心种子从 8 行补到 13 行。原来四个部门各只有 1 个成本中心，下拉框看起来像坏了。
